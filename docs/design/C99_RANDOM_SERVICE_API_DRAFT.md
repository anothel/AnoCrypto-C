# C99 Random Service Design

Status: P1-21 implemented and lifecycle-hardened engineering design.

## Purpose

The public random service provides a C99 caller-owned opaque context over the existing HMAC_DRBG-SHA-256 core and reviewed internal platform entropy provider seam.

It does not expose provider internals and does not replace the explicit-entropy DRBG API.

## Public API

```c
int ano_crypto_random_is_available(void);
const char *ano_crypto_random_service_name(void);
ano_crypto_status_t ano_crypto_random_context_size(size_t *out_size);
ano_crypto_status_t ano_crypto_random_init(void *ctx, size_t ctx_len,
                                           const uint8_t *personalization,
                                           size_t personalization_len,
                                           uint32_t flags);
ano_crypto_status_t ano_crypto_random_generate(void *ctx,
                                               uint8_t *out,
                                               size_t out_len,
                                               const uint8_t *additional_input,
                                               size_t additional_input_len,
                                               uint32_t flags);
ano_crypto_status_t ano_crypto_random_reseed(void *ctx,
                                             const uint8_t *additional_input,
                                             size_t additional_input_len,
                                             uint32_t flags);
ano_crypto_status_t ano_crypto_random_uninit(void *ctx, size_t ctx_len);
```

## Internal flow

```text
random_init
  -> module service gate
  -> OS entropy source descriptor
  -> 32-byte entropy request
  -> 16-byte nonce request
  -> HMAC_DRBG-SHA-256 instantiate
  -> source-backed marker + process guard
  -> local seed material zeroization

random_generate
  -> module service gate
  -> source-backed context check
  -> request ceiling check
  -> process marker check
  -> HMAC_DRBG-SHA-256 generate
  -> output zeroization on failure

random_reseed
  -> module service gate
  -> OS entropy source descriptor
  -> 32-byte entropy request
  -> HMAC_DRBG-SHA-256 reseed
  -> process marker refresh
  -> local entropy zeroization
```

## API behavior table

| API | Success behavior | Important failure behavior |
|---|---|---|
| `random_is_available` | Returns nonzero when a reviewed provider branch and process marker are available. | Returns zero; it does not initialize the module. |
| `random_context_size` | Returns current opaque storage size. | Returns `NOT_IMPLEMENTED` and size zero when the provider or process marker is unavailable. |
| `random_init` | Creates a source-backed HMAC_DRBG context. | Clears supplied context storage on failure. |
| `random_generate` | Produces up to 65,536 bytes per call. | Clears valid output buffers on all failures. |
| `random_reseed` | Draws fresh provider entropy and refreshes the process marker. | Returns the provider or DRBG status; no success is implied. |
| `random_uninit` | Clears supplied storage. | `NULL` with nonzero length is invalid. |

## Context separation

The explicit DRBG API and random-service API share the internal DRBG core, but their contexts have different ownership meaning.

- Explicit DRBG contexts use caller-provided entropy and remain caller-managed across process inheritance.
- Random-service contexts are marked source-backed and are tied to the reviewed platform provider policy.
- Random generate/reseed reject explicit DRBG contexts to prevent accidental presentation of caller-seeded state as the platform-backed random service.
- Public explicit-entropy DRBG generate/reseed reject random-service contexts so the platform-backed lifecycle cannot be bypassed with caller-supplied entropy.
- Cleanup remains compatible through `ano_crypto_random_uninit()` / `ano_crypto_drbg_uninstantiate()` because both only zeroize caller storage.

## Process boundary

On supported process-marker platforms, an inherited source-backed context detects a changed process identity.

- Generation returns `ANO_CRYPTO_ERR_DRBG_RESEED_REQUIRED`.
- Output is cleared.
- State is not advanced.
- The child calls `ano_crypto_random_reseed()` and retries.

This is not VM snapshot/restore, clone, checkpoint, or suspend/resume detection. Known duplicated state must be discarded and independently reinitialized.

## Threading

Global module state uses the existing internal lock seam where supported. Individual random contexts are caller-owned mutable objects and are not internally serialized.

## Sensitive data rules

Tests, examples, CI, PoC packages, and evidence may report status and byte counts but must not print or retain provider output, entropy, nonce seed material, DRBG state, or generated bytes.

## P1-20 lifecycle and ABI guardrails

- `ano_crypto_random_lifecycle_stress_tests` repeats public lifecycle operations and never persists generated output.
- The dedicated random test hook can set the private reseed counter only in tests-enabled builds; it is absent from clean Release and PoC SDKs.
- Unsupported process-marker platforms make the public random service unavailable rather than running without duplication detection.
- Clean shared Release exports must exactly match the stored 53-symbol ABI-0 name list.
