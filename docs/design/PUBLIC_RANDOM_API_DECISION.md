# Public Random API Decision

Status: P1-19 implemented engineering boundary.

## Decision

P1-19 implements the existing `ano_crypto_random_*` public symbols without adding a new public function or exposing an internal struct layout.

The service is fixed to this initial flow:

```text
reviewed platform entropy provider
  -> internal entropy adapter
  -> source-backed HMAC_DRBG-SHA-256 context
  -> ano_crypto_random_generate()
```

This is an engineering implementation step. It is not official validation evidence and does not establish suitability for every customer platform.

## Public ownership model

- The caller allocates opaque storage using `ano_crypto_random_context_size()`.
- The caller must not inspect, persist, copy, or serialize the storage.
- The context is mutable and requires caller-side synchronization when multiple threads could access the same instance.
- `ano_crypto_random_uninit()` clears the supplied storage and is allowed during error cleanup.
- A context created by the explicit-entropy DRBG API is rejected by random-service generate/reseed.
- A random-service context is rejected by the explicit-entropy DRBG generate/reseed APIs; cleanup remains common through uninstantiate/uninit.

No public provider handle, callback, source class, health-test state, or process-guard layout is exposed.

## Availability

`ano_crypto_random_is_available()` reports whether a reviewed platform provider branch is compiled and available for the current build.

Reviewed build branches in the current repository are:

- Linux `getrandom()`
- Windows `BCryptGenRandom()` with `BCRYPT_USE_SYSTEM_PREFERRED_RNG`
- Apple `SecRandomCopyBytes()`

When no reviewed provider is available:

- `ano_crypto_random_is_available()` returns `0`.
- `ano_crypto_random_context_size()` sets the output size to zero and returns `ANO_CRYPTO_ERR_NOT_IMPLEMENTED`.
- `ano_crypto_random_init()` clears caller storage and returns `ANO_CRYPTO_ERR_NOT_IMPLEMENTED`.

## Lifecycle policy

### Initialization

`ano_crypto_random_init()`:

1. validates the caller-owned buffer and flags;
2. requires the module to be operational;
3. draws 32 bytes of entropy input and 16 bytes of nonce material through the internal provider seam;
4. instantiates HMAC_DRBG-SHA-256;
5. records a private process marker for the source-backed context;
6. clears local entropy and nonce buffers on all paths.

Initialization is destructive. A failed init clears the supplied context region.

### Generation

`ano_crypto_random_generate()`:

- permits requests from 1 through `ANO_CRYPTO_RANDOM_MAX_REQUEST_SIZE` bytes;
- accepts optional additional input;
- accepts only contexts created by `ano_crypto_random_init()`;
- cannot be bypassed through public explicit-entropy DRBG generate/reseed operations;
- clears the requested output buffer on every failure after a valid output buffer is supplied;
- does not draw fresh entropy for each request;
- returns `ANO_CRYPTO_ERR_DRBG_RESEED_REQUIRED` after a detected process change or DRBG reseed-limit condition.

### Reseed

`ano_crypto_random_reseed()` draws fresh entropy through the internal provider and refreshes the process marker after success.

A manual reseed failure does not claim success and does not advance the DRBG state. If the existing process guard still permits use, the prior state remains usable; if generation is blocked by a process change, it remains blocked until a reseed succeeds.

## Unsupported behavior

- Prediction-resistance requests return `ANO_CRYPTO_ERR_UNSUPPORTED_PARAMETER`.
- Automatic reseed after `fork()` is not performed; the child must call `ano_crypto_random_reseed()`.
- VM snapshot/restore detection is not implemented.
- Suspend/resume detection is not implemented.
- Runtime provider selection and customer callbacks are not public APIs.
- Direct raw-noise acquisition and finalized source-specific health tests are not part of this service.

## Evidence and logging

Do not log or store:

- provider output;
- entropy or nonce seed material;
- DRBG key/value state;
- generated random bytes;
- private keys, tokens, or customer data.

Allowed evidence includes status names, provider branch names, pass/fail results, build metadata, source hashes, binary hashes, and package-relative manifests.

## ABI result

P1-19 changes behavior behind the P1-16 reserved symbols but adds no new exported public function. The private DRBG context layout may change before ABI freeze; callers must query the context size for each build.

## Follow-up gates

2. Decide unsupported-platform and unsupported-process-marker release policy.
3. Define VM snapshot/restore and suspend/resume operational guidance.
4. Add long-running reseed-limit and repeated lifecycle stress evidence without retaining generated bytes.
5. Re-review context-size and build-identity public layouts before ABI freeze.
6. Map the service to a final validation-target boundary only after formal scope review.
