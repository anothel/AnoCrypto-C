# Public Random API Decision

Status: P1-16 reserved boundary decision.

## Decision

P1-16 adds `include/anocrypto/ac_random.h` as a reserved public boundary, but it does not implement customer-facing random byte generation.

The current implemented random-related boundary remains:

- public explicit-entropy DRBG API in `ac_drbg.h`
- internal entropy adapter seam
- internal platform entropy provider seam
- internal HMAC_DRBG-SHA-256 instantiate/reseed helper driven by an entropy source
- tests and evidence that record status/provider names only, not entropy or generated bytes

`ano_crypto_random_*` functions are ABI placeholders. They validate arguments, enforce the module service gate where appropriate, zeroize caller output on closed-fail paths, and return `ANO_CRYPTO_ERR_NOT_IMPLEMENTED` until the public random-service policy is reviewed.

## Why not implement public random generation in P1-16

A public random service would combine several policy decisions that are not fully reviewed yet:

- entropy source selection and failure mapping
- entropy health-test strategy
- DRBG instantiation and reseed policy
- prediction-resistance behavior
- fork/process-boundary behavior
- thread-safety expectations for random contexts
- evidence capture without storing entropy, seed material, or generated bytes
- API/ABI commitment for caller-owned context layout and lifecycle

Keeping the service reserved avoids presenting an unfinished OS entropy wrapper as a stable customer random API.

## P1-16 public behavior

| API | P1-16 behavior |
|---|---|
| `ano_crypto_random_is_available()` | Returns `0`. |
| `ano_crypto_random_service_name()` | Returns status-only service name text. |
| `ano_crypto_random_context_size()` | Sets `*out_size` to `0` and returns `ANO_CRYPTO_ERR_NOT_IMPLEMENTED`. |
| `ano_crypto_random_init()` | Validates inputs, requires operational module, zeroizes context, returns `ANO_CRYPTO_ERR_NOT_IMPLEMENTED`. |
| `ano_crypto_random_generate()` | Validates inputs, rejects unsupported flags, requires operational module, zeroizes output, returns `ANO_CRYPTO_ERR_NOT_IMPLEMENTED`. |
| `ano_crypto_random_reseed()` | Validates inputs, requires operational module, returns `ANO_CRYPTO_ERR_NOT_IMPLEMENTED`. |
| `ano_crypto_random_uninit()` | Zeroizes caller storage and returns `ANO_CRYPTO_OK` for cleanup. |

Prediction-resistance flags are rejected with `ANO_CRYPTO_ERR_UNSUPPORTED_PARAMETER` until a reviewed per-request entropy policy exists.

## Relationship to DRBG API

The public DRBG API stays explicit-entropy based in P1-16. This is intentional:

```text
caller-provided entropy/nonce -> ano_crypto_drbg_instantiate -> DRBG context
```

The future public random service may use this internal flow:

```text
platform entropy provider -> entropy adapter -> HMAC_DRBG-SHA-256 -> random API
```

That future flow is not exposed as an implemented customer service in P1-16.

## Sensitive data rules

Do not log or store:

- entropy input
- nonce input used as seed material
- DRBG internal state
- generated random bytes
- private keys
- tokens
- customer data

Evidence may record only status names, provider branch names, test names, file hashes, and pass/fail results.

## Exit criteria before implementation

1. Confirm random context ownership model.
2. Confirm reseed interval and per-request limit.
3. Define fork/process-boundary behavior.
4. Define prediction-resistance support or permanent rejection policy.
5. Add health-test design and negative/failure-injection tests.
6. Add platform CI coverage for Linux, Windows, and Apple provider branches.
7. Review whether random service belongs inside the validation-target candidate boundary or a higher layer.
8. Update customer PoC package notes after public generation is implemented.
