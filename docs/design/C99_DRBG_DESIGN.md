# C99 DRBG Design Skeleton

Status: P1-19 draft.

## Implemented through P1-19

- HMAC_DRBG-SHA-256 deterministic core
- caller-provided opaque DRBG context buffer
- instantiate / reseed / generate / uninstantiate lifecycle
- public C API service gate through `ano_crypto_module_require_operational()`
- startup self-test KAT for HMAC_DRBG-SHA-256
- public KAT executable for HMAC_DRBG-SHA-256
- negative tests for entropy length, nonce length, unsupported flags, invalid state, and cleanup
- internal entropy-source driven instantiate/reseed helpers for HMAC_DRBG-SHA-256
- internal tests proving helper-driven instantiate/reseed matches explicit-entropy DRBG behavior
- boundary vectors for personalization string, additional input, reseed after generated blocks, max request size, and oversized request rejection
- internal entropy health-test attachment and fatal-failure state transition coverage
- DRBG context invalidation after a fatal reseed health-test failure

## Explicitly not implemented yet

- implemented public random-service API over source-backed HMAC_DRBG-SHA-256
- prediction-resistance requests
- Hash_DRBG-SHA-256
- automatic reseed policy exposed through a public random API
- fork/process-boundary reseed behavior
- thread-safety guarantee for shared caller-owned DRBG contexts
- finalized noise-source-specific startup/continuous health tests and thresholds

## Candidate Scope

| Algorithm | Status | Notes |
|---|---|---|
| HMAC_DRBG-SHA-256 | Implemented P1-9 slice | Deterministic core plus internal entropy-source helper. Public API still accepts explicit entropy input. |
| Hash_DRBG-SHA-256 | ABI-reserved | Returns `ANO_CRYPTO_ERR_NOT_IMPLEMENTED` from processing APIs. |

## State Model

```text
UNINSTANTIATED -> INSTANTIATED -> ERROR
        |              |
        +--------------+-> UNINSTANTIATED via uninstantiate/zeroize
```

Module state is separate from DRBG instance state. DRBG instantiate, reseed, and generate require the module to be operational. DRBG uninstantiate is allowed outside the operational state so callers can clear caller-owned context storage during cleanup.

## Public DRBG core API boundary

The DRBG core API accepts explicit entropy input:

```c
ano_crypto_drbg_instantiate(ctx, ctx_len, algorithm,
                            entropy_input, entropy_input_len,
                            nonce, nonce_len,
                            personalization, personalization_len,
                            flags);

ano_crypto_drbg_reseed(ctx,
                       entropy_input, entropy_input_len,
                       additional_input, additional_input_len,
                       flags);
```

This remains a low-level DRBG core interface. A later public random-service
layer may use the internal entropy helper, but P1-9 deliberately does not expose
that as public API.

## P1-9 internal entropy-source helper

The internal helper flow is:

```text
entropy source -> entropy input buffer -> nonce buffer -> HMAC_DRBG instantiate
entropy source -> entropy input buffer -> HMAC_DRBG reseed
```

Rules:

- helper calls are gated by `ano_crypto_module_require_operational()`
- entropy and nonce buffers are stack-local and zeroized before return
- context storage is zeroized if helper instantiation fails after the context is known to be sized correctly
- generated bytes and seed material are never printed or captured in evidence
- helper tests may compare generated outputs in memory but must not log them

## HMAC_DRBG-SHA-256 policy constants

| Constant | Value | P1-9 meaning |
|---|---:|---|
| `ANO_CRYPTO_DRBG_HMAC_SHA256_MIN_ENTROPY_INPUT_SIZE` | 32 bytes | Entropy input bytes requested from the helper source and accepted by instantiate/reseed. |
| `ANO_CRYPTO_DRBG_HMAC_SHA256_MIN_NONCE_SIZE` | 16 bytes | Nonce bytes requested from the helper source for instantiate. |
| `ANO_CRYPTO_DRBG_HMAC_SHA256_MAX_REQUEST_SIZE` | 65536 bytes | Maximum bytes per generate request. |
| `ANO_CRYPTO_DRBG_HMAC_SHA256_OUTPUT_SIZE` | 32 bytes | SHA-256 output size. |

## Sensitive Data Rules

- Do not log entropy, seed material, nonce, additional input, private scalar, generated random output, or raw key material.
- Do not include operational secret material in tests or evidence logs.
- Public DRBG KAT vectors are synthetic/public test material only.
- Zeroize DRBG context storage on uninstantiate and on fatal internal paths where possible.

## P1-16/P1-19 random-service boundary

P1-16 introduced `include/anocrypto/ac_random.h` as a reserved fail-closed ABI boundary. P1-19 implements those existing symbols with a platform-entropy-backed HMAC_DRBG-SHA-256 lifecycle without adding a public function. Builds without a reviewed platform provider report the service as unavailable and return `ANO_CRYPTO_ERR_NOT_IMPLEMENTED` from processing operations. Entropy, nonce, seed material, DRBG state, and generated bytes remain prohibited in logs and evidence. See `docs/design/PUBLIC_RANDOM_API_DECISION.md` and `docs/kcmvp/DRBG_ENTROPY_BOUNDARY_EVIDENCE.md`.

## P1-17 entropy health failure behavior

An internal entropy source may attach an internal health-test state and select operation-local or module-fatal handling. The current startup/continuous duplicate-block candidates are disabled by default and exist only to exercise bounded state, zeroization, and error transitions.

For module-fatal health failure:

1. the acquired entropy output is zeroized;
2. `ANO_CRYPTO_ERR_ENTROPY_SOURCE_FAILED` is returned;
3. the module enters sticky `ANO_CRYPTO_MODULE_STATE_ERROR_STATE`;
4. a DRBG instantiate helper clears the destination context on failure;
5. a DRBG reseed helper clears the existing DRBG context when the module has become fatal;
6. later cryptographic service calls are rejected by the module service gate.

A final source-specific health-test design, threshold, sample placement, restart policy, and recovery policy remain TODO / confirmation required.

## P1-19 source-backed process boundary

The private HMAC_DRBG context now distinguishes internally source-backed state from the public explicit-entropy path.

For internally source-backed state:

1. successful instantiation records a non-secret process marker when supported;
2. generation checks the marker before advancing DRBG state;
3. a changed marker returns `ANO_CRYPTO_ERR_DRBG_RESEED_REQUIRED` and clears requested output;
4. successful source-backed reseed refreshes the marker;
5. unsupported process-marker platforms leave the guard inactive and remain a documented limitation.

The process marker and guard type are private. No public API or struct layout exposes them. Public explicit-entropy DRBG contexts remain caller-managed; callers must not infer automatic fork/process protection for that path.

Because the private context size changed, consumers must call `ano_crypto_drbg_context_size()` and must not hard-code pre-release context sizes.
