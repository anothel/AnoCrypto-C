# AES Compiler-output Review Plan

Status: P1-26 engineering review workflow.

## Purpose

The review captures machine-code evidence for the portable AES implementation
without treating a source-level design choice as proof of emitted-code behavior.
The capture is intended to support later target-specific review and does not
replace KAT, differential testing, or platform testing.

## Capture inputs

Each artifact should identify:

- compiler family and version;
- build type and optimization configuration;
- target operating system and processor;
- shared-library SHA-256;
- disassembler identity;
- whether the AES init/encrypt/decrypt symbol markers were retained;
- the full disassembly used for manual review.

No runtime key, IV, plaintext, ciphertext, entropy, seed, DRBG state, or random
output is needed for this artifact.

## Manual review checklist

For each supported release target and compiler configuration, review at least:

1. AES key expansion;
2. forward and inverse S-box arithmetic;
3. GF(2^8) multiplication and reduction;
4. encrypt and decrypt round loops;
5. round-key address calculation;
6. temporary-state spills and stack cleanup behavior;
7. indirect branches or indexed reads whose address could depend on secret data;
8. target-specific substitutions or hardware instructions introduced by the
   compiler;
9. effects of LTO, PGO, sanitizer instrumentation, and debug settings;
10. differences between static and shared-library builds when both are shipped.

Branch and call counts generated by the capture script are descriptive only.
They are not an automated side-channel verdict.

## Hosted artifact boundary

The GitHub workflow may capture GCC and Clang x86-64 Release artifacts and may
run a cross-compiled big-endian regression lane. Workflow presence does not mean
that an artifact has been reviewed. A release evidence record must include the
specific workflow run identifier and reviewer decision before marking a target
as reviewed.
